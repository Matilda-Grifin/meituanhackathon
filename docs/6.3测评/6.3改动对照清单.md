## Rubric 到底评什么？（回答你的第 3 点）

**不完全是「只写最终参考答案一段话」。** 更准确的说法：

1. **Rubric = 从 `instructions` 拆出来的原子检查点**（一句一条，写在 `state_rubrics` / `overall_rubrics`）。例如：「方案里须体现杭州 3 日天气依据」「须指出博物馆与 14:00 东站时间过紧」「午饭须符合少油偏好」——评的是 **用户目标有没有被满足**，不是标准答案全文照抄。

2. **中间路径不扣分**：Agent 先 intake 再搜点、或直接搜点、或某步只写在回复里没走某个 skill，**只要轨迹里 assistant 的可见回复 + 真实 tool 结果能证明 rubric 成立**，就算满足。这与 VitaBench 裁判 prompt 一致：*「以 assistant 的回复及工具调用是否完成 rubric 目标为准」*，**不考核** 用了哪个 skill 名、工具调用顺序是否等于 `travel-intake → local-itinerary-planner`。

3. **例外（仍算「结果」不算「过程」）**：若某 rubric 本身要求 **可验证的事实**（如「须调用天气工具且日期对齐」「须给出驾车时长依据」），裁判看的是 **轨迹里有没有对应 tool 成功返回 + 回复是否用了该结果**，而不是规定必须第几轮、必须走哪条 skill 链路。

4. **`evaluation_criteria` 里 VitaBench 的 `required_orders`**：我们无订房/下单 MCP 时，**改写成出行版 rubric**（如「方案含符合偏好的酒店/景点名」「须说明为何选 A 不选 B」），不要照搬「订单 status=paid」 unless 你后续加了 mock 下单工具。

5. **用户模拟 LLM 说的不算分**：用户中途改口、妥协，**以 rubric 原文为准**（VitaBench：用户妥协不影响未达标 rubric）。

#### 1.5 餐饮评价语料库（仅用餐场景；ASAP + seed）

**语料范围：只做「餐饮」桶。** ASAP 几乎全是餐厅评论；景点/文化 **不走** 本库（仍用 `search_places` + `reputation` 分）。

**已找到的本仓库数据：**

| 来源 | 路径 | 用途 |
|------|------|------|
| **Mock 种子** | `workspace/mock/user_and_reviews.seed.json` + `mock_review.schema.json` | Task 的 `environment.user_reviews[]`（该用户历史短评）；filter 时作 **用户侧约束** |
| **ASAP** | `asap-master/data/`（如 `train_sample_anonymized.csv`） | 离线建 **`dining_review_index.json`**：典型评论句式 + 星级 + 18 维方面 |
| **高德搜点** | `lifecare_search_places` | 真实 **POI 身份**（id/name/type/坐标）+ `reputation` **分数**，**无** UGC 正文 |
| **yf_dianping** | 不在 Git | 本轮不用 |

离线脚本（方向）：`测试/scripts/build_dining_review_corpus.py` → 输出 `eval_cases/review_corpus/dining_review_index.json`（条目均 `is_synthetic: true`，遵守 ASAP Apache-2.0 仅离线）。

##### 1.5.1 餐饮语料库 ↔ 高德 POI **怎么对应**（核心）

**原则：不做「ASAP 某条评论 = 高德某个 poi_id」的一一绑定。**  
ASAP 里的店名/城市与高德实时 POI 对不上；正确做法是 **「高德 POI 定店，语料库按规则挂演示短评」**。

```text
高德 POI（search 结果）              餐饮语料库（离线 index）
─────────────────────              ─────────────────────────
id, name, type, address            无 poi_id 字段（不绑死）
location                           bucket = "dining"（固定）
reputation.gaode.rating  ──┐
reputation.for_weights     ├──►  star_band（见下表）
  .star_for_rank         ──┘
type 含「餐饮|美食|咖啡…」──►  判定 is_dining=true，才走语料链路
```

**Step 1 · 判定是不是「餐饮 POI」（只对这些走语料）**

| 高德 `type` 字段（示例） | 是否餐饮 |
|--------------------------|----------|
| 含 `餐饮`、`美食`、`餐厅`、`咖啡`、`茶座`、`小吃`、`甜品`、`火锅`、`中餐` 等 | ✅ |
| `风景名胜`、`博物馆`、`公园`、`购物` 等 | ❌ 跳过语料，直接进玩乐 Top-K |

（实现：`lifecare/poi_category.py` 或 filter tool 内 regex，与 `reputation._type_bucket` 的 `dining` 对齐。）

**Step 2 · 用高德侧「星级」选语料池里的 band（不是用店名去 ASAP 里搜）**

| POI 的 `star_for_rank`（或仅有 `gaode.rating`） | 语料库索引键 `star_band` |
|-------------------------------------------------|---------------------------|
| 无 rating | `band_3_4`（默认中间档） |
| 1.0～2.9 | `band_1_3` |
| 3.0～3.9 | `band_3_4` |
| 4.0～4.5 | `band_4_5` |
| 4.6～5.0 | `band_5` |

语料库每条 snippet 带 `star_band` + 可选 `aspects`（由 ASAP 列映射，如 `dish_taste→口味`、`price_cost_effective→性价比`）。

**Step 3 · 为每个餐饮候选 POI「挂载」短评（运行时，非永久写死）**

对每个 `is_dining=true` 的 POI，调用 **`lifecare_get_review_snippets`**：

| 入参 | 来源 |
|------|------|
| `poi_id` / `poi_name` + `city` | 高德 search 结果（**仅用于日志与返回体关联**，不用于 index 主键） |
| `star_band` | 由上表由 POI 的 `star_for_rank` 算出 |
| `aspect_hints` | 用户槽位 + `environment.user_reviews`（如 `少油`→偏好 `dish_taste` 非重油句式） |
| `limit` | 1～3 |

返回：`[{text, stars, aspects, star_band, is_synthetic, _note}]`，表示 **「这类店、这个星级档、这些方面」的演示短评**，不是该 POI 的真实点评。

**Step 4 · 用户历史短评（Task environment）**

`environment.user_reviews[]` 来自 seed，字段含 `user_id`、`text`、`stars`、`aspects`；filter 时与 Step 3 的 snippets **一起** 判断 POI 是否保留（如用户历史写「少油」、snippet 写「太油」→ 倾向剔除）。

**明确不做：** 用 ASAP 原文当 `keywords` 搜高德；不把语料库条目写入 POI 的 `id` 字段；景点类不调用 `get_review_snippets`。

### 二、【调度器】Orchestrator

**VitaBench 原值 vs 本项目（已确认）：**

| 参数 | VitaBench 默认 | **本项目采用** | 含义 |
|------|----------------|----------------|------|
| **`max_steps`** | 300 | **`100`（允许配置 80～120）** | 一步 = Agent/User/Env 之间 **一次消息转发**（含每次 tool 往返），不是「模型对用户答 100 次」 |
| **`max_errors`** | 10 | **10** | 工具累计失败达上限 → `too_many_errors`，**reward = 0** |

触顶语义与 VitaBench 相同（`evaluator.py`：`max_steps` / `too_many_errors` → reward 0）。300 是酒旅长任务保险丝；本地出行 + 少量 MCP，**80～120 足够**，默认 **100**，写进 `config.json` → `orchestrator.max_steps`。

| 改什么 | 现在 | 要改成 |
|--------|------|--------|
| 终止（正常） | 轮数用完（多轮 `max_turns: 6`） | 用户模拟 LLM 或 Agent 输出 **`###STOP###`** |
| 终止（护栏） | 无统一 Orchestrator | **`max_steps=100`（80～120）**、**`max_errors=10`** |
| 提前终止打分 | — | 触顶或工具错误过多 → **rubric reward = 0** |
| 轮次 | 固定 6 轮设计 | **不设测评目标轮次**；报告记录 **实际 step 分布**（均值/P95） |

## 原测评指标对照表（回答你的第 4 点）

下面是你 **6.2 选型链路** 里实际在用的指标（来源：`score_dimensions.json`、`rubric.json`、`task_metrics.py`、`process_metrics.py`、`multiturn_metrics.py`、`config.json` → `generate_report.py`）。改 Task 库 + 双 LLM 后，逐项说明 **还能不能用**。

### A. 报告主指标（答辩常用）

| 原指标 | 原来怎么算 | 改库后 |
|--------|------------|--------|
| **任务成功率 `task_success_rate_pct`** | `task_metrics.compute_task_success`：规划类要 **总分≥60、方案分≥70、工具预算不超标、无 intake 前搜点** 等 | ❌ **废弃作主指标** → 换成 **平均 rubric reward**（及 reward=1.0 的比例，可称 Pass@1） |
| **平均分 `avg_total_score`（0～100）** | 六维加权（见 B） | ❌ **废弃作主指标**；若需要可保留「首字时长、成本」类 **非 LLM 硬指标** |
| **通过率 `pass_rate`** | `total_score ≥ 60` 的题占比 | ❌ 废弃；可改为 **`reward ≥ 1.0`** 或 **`reward ≥ 0.8`**（阈值你定） |
| **分难度** easy / medium / hard | 按 case 的 `difficulty` 聚合上面三项 | ✅ **保留结构**，聚合对象改为 **rubric reward** |
| **单轮 vs 多轮两套成绩** | config 两套 dataset | ❌ **取消**；只有 50 Task，报告里改 **「对话轮数分布」** 替代 |

### B. 六维细则分（`score_dimensions.json`，权重合计 100）

| 维度 | 权重 | 原来评什么 | 改库后 |
|------|------|------------|--------|
| **首响时效** `first_response` | 15 | 首轮 TTFT ≤10s/15s/25s 或可见 intake | ✅ **保留为北极星之一**（见 **H 节**）；与 rubric reward **分开算**，Orchestrator 采 `time_to_first_assistant_text_ms` / `time_to_first_progress_ms` |
| **交互补槽** `intake_flow` | 15 | 槽位不齐时首轮须 A/B/C 选择题 | ❌ 过程指标；用户模拟 LLM 可能 **口语补槽** 而非选择题 → **废弃**（除非某 rubric 写「须确认人数」） |
| **工具执行** `tool_execution` | 25 | 是否命中 rubric 框架：天气 / 搜点 / 路线 **角色** | ❌ 过程指标；若 rubric 写「须基于天气工具结果」由 **打分 LLM** 判，不单独占 25 分 |
| **约束诚实** `constraint_honesty` | 10 | 用户未给人数则回复不 preset 人数 | ⚠️ 可 **写进 rubric**（一条检查点），不再全局正则 |
| **方案完整** `plan_completeness` | 20 | 回复含餐饮+文娱、时段、≥2 地点 | ⚠️ 拆成 **多条 rubric**（午饭、动线、天数） |
| **可执行性** `executability` | 15 | 高德链接 / 分钟数 / 天气依据 | ⚠️ 拆成 **rubric**（「含路程时间依据」等） |

### C. 全局规则（`rubric.json`，7 条自动规则）

| 规则 id | 原来评什么 | 改库后 |
|---------|------------|--------|
| `must_intake_first_turn` | 槽位不齐须选择题 | ❌ 废弃（过程） |
| `no_search_route_before_intake` | 槽位不齐禁止先搜/算路 | ❌ 废弃（过程） |
| `no_preset_party_size` | 未给人数不能写死 | ⚠️ → **可选 rubric** |
| `weather_must_call_tool` | 问天气须调工具 | ⚠️ → **rubric**「须基于天气工具」 |
| `plan_must_search` | 规划须搜 POI | ⚠️ → **rubric**「方案须引用真实 POI/检索结果」 |
| `plan_full_chain` | 须 weather→search→route | ❌ 废弃（过程链；与你第 3 点冲突） |
| `first_turn_responsive` | 10s SLA | ✅ 并入 **`first_response` 北极星**（与 `score_dimensions.py` 同源） |

### D. 北极星 `task_success` 的附加逻辑（`task_metrics.py`）

| 类型 | 原来 | 改库后 |

| 指标 | 改库后 |

### H. 改库后「北极星 + 辅指标」一览（已确认）

#### 北极星（答辩主看这三项）

| 指标 | 怎么算 | 说明 |
|------|--------|------|
| **① Mean Rubric Reward** | 50 题平均：`满足的 rubric 数 / 该题总 rubric 数` | 任务 **做没做对**（6.3 主 reward） |
| **② Full Success Rate** | reward = **1.0** 的题占比 | 可称 Pass@1 / 「任务成功率」 |
| **③ 首响时效 `first_response`** | 每题 0～100 分，再聚 **均分** 或 **达标率** | **沿用现网口径**（`score_dimensions.py` → `_score_first_response`），与 rubric **独立** |

**`first_response` 单题计分（与 6.2 一致，不改档）**：

| 条件 | 得分 |
|------|------|
| 有计时：首轮 TTFT（`time_to_first_assistant_text_ms` 或 `time_to_first_progress_ms`）**≤ 10s** | **100** |
| **≤ 15s** | **70** |
| **≤ 25s** | **40** |
| **> 25s** | **10** |
| 无计时数据：槽位未齐且首轮可见 **intake 选择题**（A/B/C 模式） | **85** |
| 无计时：首轮有可见文字或工具/进度 | **75** |
| 无计时且无可见进展 | **40** |

报告建议同时给：**Avg First Response Score**、**First Response Pass Rate**（例如单题 ≥70 分算达标，阈值可在 `config.json` 写死）。

#### 辅指标（报告 / 成本，不作北极星）

| 指标 | 说明 |
|------|------|
| 分难度 reward / first_response | easy / medium / hard |
| 首字 P50/P95（ms） | 原始耗时分布，与上分档互补 |
| 实际对话步数/轮数 | 不定轮次后的可观测性 |
| Token / 工具次数 / 总耗时 | 选型成本 |
| 提前终止率 | 触达 **`max_steps=100`** 或 **`max_errors=10`** → rubric reward 0 的占比 |

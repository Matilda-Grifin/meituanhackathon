## 一、测评在做什么

在统一仿真环境与任务集上，评估 **豆包 Seed 2.0 Lite** 作为「本地生活出行规划 Agent」大脑是否可用。流水线沿用 VitaBench 四段式：

```
用户模拟器 → 助手（OpenClaw 网关 + MCP：天气/高德 POI/算路）→ 多轮对话 → 用户结束
                                                    ↓
                              裁判按检查清单滑动窗口打分 → 得分率 + 首响相关字段
```

每题含：仿真环境、用户画像、隐藏任务指令（仅用户模拟器可见）、检查清单（仅裁判可见）。主分是「检查项得分率」，不是人工观感分。

### 为何有的批是 49 题、有的是 50 题

批跑脚本默认 `--exclude T063_007`。`T063_007`（苏州园林半日）是流水线 **冒烟题**，**有 Harness** 全量 batch 跳过。题目文件本身在考卷中；**无 post_output** 批刻意纳入 007，故为 **50/50**。

## 二、指标怎么读

| 指标 | 含义 |
|------|------|
| **检查项得分率（主）** | 满足条数 ÷ 该题总条数；全部满足 = 满分题 |
| **满分率** | reward = 100% 的题占比 |
| **≥80% 部分成功** | 「大体可用」辅线 |
| **首响分 first_response** | 首轮体验分。采集到首字耗时则按阈值打分；未采集但有首轮进展记 **75** |
| **首轮助手耗时** | 轨迹里首条 assistant 的 `duration_ms`（**整轮回复时长**，不是严格首字） |
| **助手合计耗时** | 各轮 assistant `duration_ms` 之和，近似任务总时延 |
| **结束方式** | `user_stop` = 用户模拟器判定可结束（本次全部如此） |

**时延说明**：本次 49 题 `time_to_first_assistant_text_ms` 均为空，首响分全部为 75（`progress_no_timing`）。答辩若需「首字 <5s」需另开带 TTFT 采集的评测；本次只能报 **首轮整段耗时**。

### Seed：有 Harness vs 无 post_output（49 题重叠）

隔离条件：侧车进程、`LIFECARE_DISABLE_POST_OUTPUT=1`，**不改** `openclaw.json` / 线上 `run_mcp.py` / SOUL。轨迹里 harness 各 turn `skipped=true`（checklist / POI 修复未写回）。

| 指标（重叠 49 题） | 有 Harness | 无 post_output | Δ（无 − 有） |
|--------------------|------------|----------------|--------------|
| 平均得分率 | 72.5% | **约 74.0%**‡ | **约 +1.5pp** |
| 满分 | **10** | 7 | −3 |
| ≥80% | 23 | 24 | +1 |

‡无 post 批总均分 73.8% 含 `T063_007`；与 49 题重叠集上均值差约 +1.5pp。

**无 post 显著变好（Δ≥+0.5）的例子**：`T063_020` 0→100%、`T063_026` 0→88.9%、`T063_013` 0→87.5%、`T063_037` 25→100%、`T063_041` 33→100%。  
**无 post 显著变差（Δ≤−0.4）的例子**：`T063_031` 87.5→0%、`T063_035` 100→37.5%、`T063_016` 62.5→12.5%、`T063_048` 100→55.6%。

解读：关掉 post_output **没有**拉开稳定大赢面；均分接近、满分反而下降。Harness 更像「压低极端零分 / 抬满分交付」的护栏，而不是抬全面均分的唯一杠杆。答辩口径仍以 **有 Harness + Seed** 作现网代表；无 post 批用于归因，勿说成「关 Harness 更好」。

### Qwen 改前暴露的问题 → 我们修了什么

Qwen 全量 50 题基线的主要短板集中在四类：**助手异常（9 题记 0 分）**、补全需求阶段过早调用工具、方案结构不完整，以及引用未检索到的 POI。随后我们补齐系统侧护栏，并以 10 题子集复测；现网 Agent 换用 Seed，在接近全量考卷（缺冒烟题 1 题）上重跑。

| 改动 | 解决什么 | 落地方式 |
|------|----------|----------|
| **阶段门禁** | 需求未问清即检索门店 / 规划路线 | 信息采集阶段禁止检索与算路；关键槽位齐全后才进入规划 |
| **出方案 Checklist** | 声明已完成，但缺失天气、预算、路程或结构板块 | 长文输出前校验必备段落；缺失项按模板自动补全 |
| **POI 白名单** | 编造本轮未检索到的门店 | 方案中的门店名称必须来自本轮检索结果；名单外名称在系统内静默替换 |
| **角色与技能约束** | 天气不落地、交通不可执行、多轮局部乱改 | 要求独立天气段落；交通统一写明「打车约 X 公里 / Y 分钟」；需求变更则重出完整方案 |
| **评测对齐线上终稿** | 裁判原按模型原稿打分，与用户可见内容不一致 | 测评链路接入与线上一致的出方案修复，裁判按修复后终稿评分 |
| **工具失败降级** | 外部接口失败时仍编造门店或气温 | 明确标注能力降级；禁止伪造实时链接与虚假气温 |

历史答辩口径（系统侧改前→改后）：任务成功率约 **82%→90%**，工具调用精确率约 **66%→95%**，玩乐与餐饮双类型覆盖约 **70%→100%**。本报告以实测结果为准；改后 Qwen 仅有 10 题子集，不宜外推为全量 50 题结论。

## 四、低分题归因（摘要）

零分 / 极低分并非「模型完全不可用」，多为 **对话未交付完整方案就被用户模拟器结束**，裁判检查项全未满足。

| 题号 | 得分 | 场景 | 现象 |
|------|------|------|------|
| T063_013 | 0% | 长沙商场亲子半日 | 仅 1 步，仍停在补槽选择题，未出方案 |
| T063_026 | 0% | 青岛鲁菜半日 | 仅 1 步，仍停在出发时间/类型追问 |
| T063_020 | 0% | 上海城市一日 | 8 步仍在类型/时间选择题，未进入有效规划交付 |
| T063_037 | 25% | 深圳城市一日 | 工具暂不可用提示 + 格式混乱链接，检查项几乎未过 |
| T063_041 | 33% | 上海赶高铁半日 | 约束满足不足 |
| T063_036 | 38% | 重庆火锅半日 | 约束满足不足 |

改进方向：补槽阶段压缩轮次、防止用户模拟器过早 `user_stop`；工具失败时的降级话术与输出格式护栏（Harness）。

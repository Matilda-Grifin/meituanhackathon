## Slide 02 · 我们做了什么

### 页面标题

**星途生活：帮用户把半下午逛吃，一次说清楚**

### 主文案（页面主体，建议左对齐）

星途生活是一款跑在 OpenClaw 对话框架上的**本地路线规划 Agent**。  
用户用日常口语描述需求，系统先快速问清 2～3 个关键信息，再调用真实地图和天气数据，输出带时间表、店铺卡片和路线地图的完整方案；之后还能用一句话改午饭、改节奏，不用从头再来。

它和搜索推荐最大的区别是：**不是扔给用户一堆候选店，而是直接交一条排好顺序、算好路程的动线。**

### 三个核心数字（横排大卡）

| 数字 | 标签 | 白话解释 |
|------|------|----------|
| **< 5 秒** | 首次可见回应 | 用户发话后几秒内就会出现选择题或进度提示，不用对着空白屏等 |
| **90%** | 规划完整通过率 | 50 道标准测试题里，九成的方案通过了全部质量检查（含餐饮+玩乐、至少 3 个地点、天气与路线等） |
| **≥ 3 个** | 每方案地点数 | 每条路线至少串联 3 个真实地点，且覆盖吃饭 + 玩乐/文化两类 |

### 口播

我先给结论。星途生活解决的是本地半日出行规划：用户说人话，系统交路线。  
速度上，首次回应多数在 5 秒左右；质量上，50 道题测下来完整通过率 90%；每条路线至少 3 个真实地点，吃饭和玩乐两类都覆盖。

## Slide 03 · 痛点：规划半下午，为什么这么累

### 页面标题

**一次周末出行，用户要在多个 App 之间来回拼**

### 场景故事（建议占半页，可配插画）

周六上午 10 点，小陈难得不用加班。他在美团里输入：  
下午有空，想和朋友在公司附近逛三四个小时，吃点本地的，预算别太高，别排太满。

接下来典型路径是：在点评搜公园或展览 → 打开地图看距离 → 再搜午餐 → 心算闭馆时间和排队 → 发现博物馆周一不开，重来一遍。  
**同一件事，信息散在三四处，用户自己当调度员。**

### 四类具体问题（2×2 卡片）

| 问题 | 用户侧感受 |
|------|------------|
| 信息碎片化 | 店名、评价、距离、营业时间分散在不同界面，拼起来费时 |
| 等待没反馈 | 有些 AI 助手长时间空白，用户不知道是在算还是在卡死 |
| 回答太浅 | 只给两三个店名，没有按时间排好的「先玩哪、再吃哪、怎么过去」 |
| 结果不稳定 | 同一句话问两次，方案质量差很多，不敢真按它出门 |

### 竞品实测结论（一行收束）

立项时我们测过 OTA 内置 AI、独立出行 App、小红书点点和美团小团：  
**快的往往不够深，深的往往不够稳，朋友感强的往往缺完整路线表。** 星途生活要在一条链路上同时补深度和稳定性。

### 口播

痛点不用讲抽象概念。用户要的是半下午行程，现实却是自己搜、自己算、自己排。  
更麻烦的是，很多助手要么等太久，要么只给几个店名，要么每次答都不一样。  
所以我们做的不是又一个聊天框，而是一条能照着走的路线。

## Slide 04 · 星途生活的三个特点

### 页面标题

**三个特点：快、全、稳**

### 说明段（页面上半区）

星途生活不是聊两句推荐三家店，而是交付一整条本地路线：几点去哪、中间怎么移动、吃什么、下一站在哪。  
下面三个特点，是答辩和 Demo 最该记住的核心。

---

### 特点一 · 快：说完话，几秒内就有回应

**用户要什么**  
发出第一句话后，不能对着空白屏干等。

**我们怎么做**  
把对话拆成两阶段：关键信息还没问全时，只出 2～3 道点选题，先不查地图；信息齐了，再并行查天气、搜店、算路。  
多数场景下，5 秒内就会出现选择题或进度提示。

**数据**  
50 道自动化测试 + 现场 Demo 均可复现；优化后首次可见回应从约 10 秒压到 5 秒以内。

---

### 特点二 · 全：吃饭、玩乐都有，至少串 3 个真实地点

**用户要什么**  
半下午行程，不能只有一顿饭或只有一个景点。

**我们怎么做**  
规划时强制覆盖餐饮 + 玩乐/文化两类；每条路线至少 3 个真实地点，相邻点之间用地图 API 核算驾车或步行距离，时间表留足移动和用餐时间。

**数据**  
测试题里两类都有、地点够数的检查项，当前覆盖率 100%。

---

### 特点三 · 稳：同一需求，质量不飘

**用户要什么**  
问两次，不能一次很好、一次漏查天气或漏吃饭。

**我们怎么做**  
三层保障：① 阶段规则——该查天气时必须查，信息没问完不能乱搜店；② 四个能力模块分工，不靠一条 prompt 硬写；③ 50 道题批量回归，改代码后重跑对比。  
11 个候选大模型横向评测后，选定综合表现最好的 Seed 2.0 Lite 作为默认。

**数据**  
完整方案通过率 82% → 90%；工具调用准确率 66% → 95%。

## Slide 05 · 产品是什么

### 页面标题

**星途生活：在对话里交付一整条本地路线**

### 产品定位

- **答辩全名**：星途生活 StarRoute  
- **中文副标**：顺路  
- **对话助手**：小星（Demo 顶栏、口播 Demo 时使用）  
- **形态**：移动优先的对话界面（手机浏览器即可体验）  
- **一句话**：不是推店名单，是排好顺序、算好路程、写好时间表的半日方案  

### 和传统路径对比

| | 传统搜索 / 推荐 | 星途生活 |
|---|----------------|----------|
| 交付物 | 候选列表，用户自己挑、自己串 | 按时间排好的完整行程 |
| 交互 | 表单或多轮搜索 | 一句口语 + 少量点选 |
| 过程感知 | 常黑盒等待 | 聊天气泡里可见「正在查天气、搜店、串路线」 |
| 改需求 | 往往重新搜一遍 | 在原方案上局部修改，不重走问卷 |

### 对本地生活场景的价值（一段话）

用户在点评、美团里本来就会搜店、看评价；星途生活把「搜」推进到「排好一整条」——决策在对话里完成，路线里的每一家店仍可通过卡片跳转地图详情，**缩短从「想出去玩」到「敢出门」的路径**，而不是多一个孤立的聊天框。

## Slide 07 · 体验创新

### 页面标题

**看起来像消费级产品，不像工程师调试台**

### 导语

我们判断：工具感来自两层——**界面像控制台**加上**回答像报告**。只改一层不够，所以 UI 和 Agent 语气同步调整。

### 四项体验创新（每项：问题 → 做法 → 用户得到什么）

**1. 聊天气泡里的进度提示**  
- 问题：底部「任务 4/5 步」像后台日志，C 端用户会懵。  
- 做法：进度收进对话流，单行朋友化文案，如「正在查申园…」。  
- 结果：等待可理解，不破坏聊天节奏。

**2. 可点选的信息确认**  
- 问题：让用户打字补预算、偏好，摩擦大且容易漏填。  
- 做法：A/B/C/D 按钮点选；确认前不触发地图重查询。  
- 结果：首响快，补信息也轻松。

**3. 店铺横卡内嵌在方案里**  
- 问题：纯文字方案里店名、链接、图片重复出现，难扫读。  
- 做法：借鉴小团式横卡——图、评分、人均、距离；整卡跳转高德。  
- 结果：方案可扫、可点、可落地。

**4. 分层交付：文字 → 地图 → 一览图**  
- 问题：长方案 + 生图一起出，用户要等很久才看到第一个字。  
- 做法：文字先流式输出；地图跟进；行程一览图异步插入（约 50 秒级）。  
- 结果：先能用，再更好看。

### UI 与 Agent 双层「朋友化」

| 层 | 以前 | 现在 |
|----|------|------|
| 界面 | 角色标签、黑底表格、双滚动条 | 点评橙 + 浅色泡，仅聊天区滚动 |
| 语气 | 「您好，已为您查询」 | 「周六人不少，我按轻松节奏给你排的」 |

### 口播

体验上四件事：进度进气泡、信息用点选、店铺用卡片、内容分层出。  
同时 UI 和说话方式一起改，让评委感觉这是能放进本地生活 App 对话入口的形态，而不是 Hackathon 临时界面。

## Slide 08 · 技术方案（评委友好版）

### 页面标题

**真实数据算路 + 系统护栏，保证又快又稳**

### 一段话讲清架构

用户在手机 App 或网页发消息 → OpenClaw 网关维持多轮对话 → **人设与阶段规则**决定现在是「补信息」还是「出方案」→ 四个**能力模块**分别负责问需求、排行程、算路程、读偏好 → **质量护栏**拦截乱调工具、修复输出格式 → 外部接高德地图店铺与路线、Open-Meteo 天气，热点数据走 Redis 缓存。

**Agent 不是写死的脚本**：每一步根据真实搜店结果动态决定下一站，但护栏保证不会信息没问完就去搜店。

### 四项关键技术

| 设计 | 解决什么 | 白话 |
|------|----------|------|
| 两阶段对话 | 首响慢 | 信息齐之前只问问题，不齐不查地图 |
| 能力模块拆分 | 难维护 | 问需求、排行程、算路、偏好分开，像插件一样组合 |
| 质量护栏 | 乱调工具、瞎编店名 | 该查天气时必须查；方案格式坏了自动修 |
| 真实数据 + 模拟偏好 | 假数据不可信 | 店和路线来自高德；点评偏好用语料模拟，不碰真实隐私 |

### 口播

技术上是「模型想步骤 + 地图给真实数据 + 护栏保底线」。  
评委不必记 OpenClaw 这个词，可以把它理解成：能记住对话、能调地图、能流式输出的 Agent 底座。  
我们在此基础上做了阶段控制和测评闭环，所以不是 Demo 能跑，而是批量测也稳。

